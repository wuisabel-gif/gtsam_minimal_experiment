§ 00

Why offline, why repeatable

Live sensor reading is not always successful during hardware sessions. These conditions make it hard to tell whether a graph problem is the math or the deployment — so the suite removes that ambiguity entirely.

hardware session · status feed
CAMERAcameras can reboot or disconnect mid-run
DVL / DEPTHDVL or depth sensors may be unavailable
TOPICSIMU, DVL, depth, and camera topics may not all be live at the same time
RUNTIMEcontainer / runtime issues can hide whether a bug is math or environment

The graphs here are built from standard GTSAM library primitives — PreintegratedImuMeasurements, ImuFactor, PriorFactorPose3, LevenbergMarquardtOptimizer and friends — then adapted to the Barracuda AUV measurement layout. The structure isn't invented; it's a vehicle-specific experiment on top of the standard factor and IMU preintegration machinery.

§ 01

What this repository tests

Eight offline tests, ordered from the most underwater-specific prototype down to small reference graphs and real-data fallbacks.

1

Synthetic underwater multi-sensor graph

generate_synthetic_dataset.py run_gtsam_localization.py

The main underwater-oriented offline prototype. Built on GTSAM's inertial and factor-graph workflow, then adapted to the Barracuda measurement layout.

  • IMU motion propagation / preintegration
  • depth constraints
  • DVL velocity constraints
  • pose / velocity / bias state layout
  • batch GTSAM optimization
2

Simple Pose2 batch sanity test

pose2_slam_sanity.py

A small reference graph for checking the basics of batch optimization behavior.

  • prior factor setup
  • BetweenFactorPose2
  • loop closure
  • batch optimization behavior
3

Simple Pose2 incremental iSAM2 test

pose2_isam2_incremental.py

The incremental version of the simple pose graph — useful for checking the online update flow.

  • online / incremental graph update flow
  • basic iSAM2 usage
  • incremental vs raw odometry
4

Backend-only replay test for the ROS2 estimator

replay_estimator_backend.py

Replays the synthetic underwater dataset directly through barracuda_estimation.gtsam_estimator.GtsamEstimator without ROS2 — the closest offline test of the actual backend logic.

  • IMU buffering
  • depth ingestion
  • DVL ingestion
  • backend update flow
  • step-by-step estimator status
5

Rosbag-to-dataset conversion

rosbag_to_gtsam_dataset.py

Converts a ROS2 bag into the .npz format expected by the offline underwater runner.

  • /barracuda/imu/data
  • /barracuda/depth
  • /barracuda/dvl/odometry
  • sensor_msgs/msg/Range
  • sensor_msgs/msg/FluidPressure
6

Rosbag recording helper

record_barracuda_rosbag.sh

A small helper script for recording Barracuda estimation topics into a ROS2 bag.

7

Real-data fallback Pose2 graph

run_pose2_from_rosbag.py

When the full sensor stack is unavailable but a live pose topic like /barracuda/zed_node/pose exists, this builds a simple offline Pose2 graph from the recorded stream.

  • real-data fallback testing
  • checking the pipeline works at all
  • pose-graph behavior without DVL / depth
8

Real-data offline Pose3 graph

run_pose3_from_rosbag.py

The 3D version of the rosbag pose test — keeps x, y, z and full 3D orientation, so vertical motion and orientation aren't flattened into a yaw-only result.

  • vertical motion is preserved
  • orientation stays full 3D
  • live pose tested in full 3D offline
§ 02

Why these tests matter

Intentionally smaller and cleaner than the final vehicle stack, so each one answers a single sharp question.

questions this suite can answer
Q · STRUCTUREis the graph structure correct?
Q · FACTORSare we using the right factors?
Q · DEPTHdoes z survive a Pose3 pipeline?
Q · SOURCEis a bug GTSAM logic or live ROS deployment?
Q · PROGRESScan we still validate when hardware is partially unavailable?

Because the workflow is rosbag-based, the pattern reaches past this one vehicle: any ROS2 system that records pose, IMU, odometry, or depth can reuse the same offline validation approach to test factor-graph estimation without depending on a perfect live run.

§ 03

Run

Each script is standalone. Start small, then move up to the synthetic underwater graph and real rosbag conversions.

core suite
# run the offline tests, smallest first
python3 generate_synthetic_dataset.py
python3 run_gtsam_localization.py
python3 pose2_slam_sanity.py
python3 pose2_isam2_incremental.py
python3 replay_estimator_backend.py
python3 run_pose2_from_rosbag.py /root/bags/my_bag
python3 run_pose3_from_rosbag.py /root/bags/my_bag
convert a real Jetson rosbag → underwater dataset
python3 rosbag_to_gtsam_dataset.py /root/bags/my_bag \
  --output data/jetson_rosbag_underwater.npz
python3 run_gtsam_localization.py \
  --dataset data/jetson_rosbag_underwater.npz \
  --output-dir results_jetson_rosbag
fallback · pose topic only (no DVL / depth)
# Pose2 fallback graph from a live pose stream
python3 run_pose2_from_rosbag.py /root/bags/my_bag \
  --pose-topic /barracuda/zed_node/pose \
  --output-dir results_pose2_rosbag

# verify z directly with the Pose3 version
python3 run_pose3_from_rosbag.py /root/bags/my_bag \
  --pose-topic /barracuda/zed_node/pose \
  --output-dir results_pose3_rosbag

§ 05

Intended workflow

A real sequence — validate the cheapest, most controlled graphs first, and only promote logic once it's stable.

  1. Validate small graphs first
    Pose2 batch & iSAM2 reference graphs.
  2. Validate synthetic underwater multi-sensor graphs
    IMU + depth + DVL on a controlled synthetic dataset.
  3. Validate rosbag-based fallback graphs from real topics
    Pose2 / Pose3 from a live pose stream.
  4. Replay cleaned-up logic into the ROS2 estimator backend
    Offline replay through GtsamEstimator.
  5. Move stable graph logic into the live estimator package
    Only once everything above holds — into barracuda_estimation.
